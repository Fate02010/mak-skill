# Step 7：审视检查，提出改进建议

**目标：** 从架构师视角全面审视生成的 SQL，发现问题并提出改进建议；如果设计影响了领域模型，必须同步更新 `领域模型.md`。

## 执行步骤

### 阶段 7-1：全面审视

读取 `WORK_DIR/[产品名称].sql` 和 `WORK_DIR/领域模型.md`，从以下 5 个维度检查：

**1. 完整性**
- 领域模型中的所有实体是否都有对应的表？
- 多对多关系是否都有中间表？
- 是否缺少必要的日志表、状态流转记录表？

**2. 规范性**
- 所有字段是否都有 COMMENT？
- 主键类型是否为 BIGINT（兼容雪花算法）？
- 公共字段（created_at、updated_at、deleted_at 等）是否一致？
- 命名规范是否统一（下划线命名法）？

**3. 性能**
- 高频查询字段（WHERE/JOIN 条件）是否有索引？
- 是否存在可能导致全表扫描的设计？
- 大字段（TEXT/BLOB）是否考虑分离存储？
- 预估数据量大的表是否考虑了分区/分表策略？

**4. 业务正确性**
- 字段类型和长度是否合理？
- 枚举值（TINYINT/状态码）是否在 COMMENT 中说明含义？
- 外键设计是否与业务规则一致？
- 唯一约束是否覆盖了业务唯一性要求？

**5. 领域模型一致性**
- 生成的表结构与领域模型是否一致？
- Step 6 收集的领域模型反馈是否需要处理？

### 阶段 7-2：向用户展示审视结果

```
=== 数据库设计审视报告 ===

【完整性】✅ 无遗漏 / ⚠️ 发现以下问题：
  - 缺少退款表（order_refund），建议新增

【规范性】✅ 符合规范 / ⚠️ 发现以下问题：
  - product_sku.status 缺少 COMMENT 说明枚举值含义

【性能】✅ 索引合理 / ⚠️ 建议优化：
  - order 表按 user_id 查询频繁，建议添加 idx_user_id 索引
  - order_item 表数据量大，建议考虑按 order_id 哈希分区

【业务正确性】✅ 规则一致 / ⚠️ 发现以下问题：
  - 订单状态值未在 COMMENT 中说明（1=待支付 2=已支付...）

【领域模型一致性】✅ 一致 / ⚠️ 需更新领域模型：
  - 新增 order_refund 表未在领域模型中体现

---
是否应用以上改进建议？（回复"全部应用"/"选择应用 1,3"/「"不需要"）
```

### 阶段 7-3：应用改进

根据用户选择，修改 `WORK_DIR/[产品名称].sql` 中对应的内容。

### 阶段 7-4：更新领域模型文档（如有影响）

**如果审视过程中发现设计影响到领域模型（新增实体、修改关系等），必须更新 `WORK_DIR/领域模型.md`：**

1. 在对应聚合的实体列表中新增或修改条目
2. 更新实体关系总览
3. 在变更记录中追加：

```markdown
| v1.1 | 新增 order_refund 实体（退款）| SQL 设计阶段发现业务完整性问题 |
```

更新完成后告知用户：`领域模型.md 已同步更新（v1.1）`

### 阶段 7-5：输出完成报告

```
=== 数据库设计完成 ===

输出文件：
  - [WORK_DIR]/[产品名称].sql    （最终建表脚本，共 [N] 张表）
  - [WORK_DIR]/领域模型.md       （v[X]，[是否/已更新]）
  - [WORK_DIR]/RountMap.md      （资料索引）

如需增量调整（新增表、修改字段），下次启动时选择增量模式（Step 8）。
```

## 增量改进循环

Step 7 审视完成后，用户可继续提出改进需求。每轮改进：
1. 修改 SQL 文件
2. 若影响领域模型，同步更新 `领域模型.md` 并记录变更
3. 以用户"不需要"或"完成"为终止信号
