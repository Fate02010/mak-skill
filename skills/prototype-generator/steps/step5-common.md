## 阶段 5-1：读取需求，功能划分

**⚠️ 功能模块定义（draw.io 模式 sheet 命名强制规则）：**

"功能模块"= **业务域**，以产品功能命名，**不是系统层或技术层**。

| ✅ 正确（业务域）| ❌ 错误（系统层/技术层）|
|----------------|------------------------|
| 用户模块 | APP系统 |
| 商品模块 | 后台管理 |
| 订单模块 | 移动端 |
| 支付模块 | Web端 |
| 营销模块 | 前台 |

> "APP系统"不是一个功能模块，它包含多个功能模块（用户、商品、订单等），必须继续拆分。
> "后台管理"同理，必须拆分为具体的功能模块（权限管理、内容管理、数据统计等）。
> **每个 draw.io sheet 只对应一个具体业务域，sheet 名 = 模块名（如"订单模块"）。**

**sheet 命名硬规则（必须遵守）：**

- 允许的推荐格式：`后台-员工管理`、`后台-订单管理`、`后台-发货单管理`、`小程序-首页`、`小程序-会员中心`、`溯源展示`
- **禁止出现中间产物前缀**：`page_spec:`、`page_spec：`、`spec-`、`tmp-`
- **禁止使用系统层笼统名**：`后台管理`、`APP系统`、`小程序端`、`Web端`
- **禁止使用大杂烩并列命名**：`人员与权限`、`商品与内容`、`订单与履约`、`会员与营销`、`账号与首页`
- 一个 sheet 名最多只表达**一个终端维度** + **一个具体业务模块**；若出现“与 / 和 / 及 / /”连接多个业务域，必须拆分
- 登录页、工作台、导航图可作为少数例外独立命名，但也必须具体，如 `后台-登录页`、`后台-工作台`、`导航-页面跳转地图`

**模块粒度硬限制（必须遵守）：**

| 规则 | 限制 | 违反时动作 |
|------|------|-----------|
| 每个模块管理的业务实体数 | **列表/CRUD 类模块 ≤ 1 个；登录/工作台/首页可例外** | 按业务实体拆分为多个模块 |
| 每个模块的 swimlane 数（含弹窗） | ≤ 6 个 | 拆分为多个模块 |
| 每个模块的列表页数 | ≤ 2 个 | 多于 2 个列表页说明包含多个实体，必须拆分 |

**拆分判定流程：**
1. 列出该模块所有列表页 → 每个列表页管理一个业务实体
2. 若同一模块中出现两个以上不同业务对象（如员工、角色、部门、司机）→ 按业务实体拆分
3. 若模块名里出现 `与/和/及/` 或系统层前缀+并列业务名 → 先重命名/拆分，再继续
4. 每个拆分后的模块包含：该实体的列表页 + 新增/编辑弹窗 + 删除确认弹窗 + 详情页（若有）

**示例：**
- ❌ "后台管理-核心业务"含：商品管理 + 会员管理 + 订单管理 + 发货单管理（4 个列表页，4 个业务实体）
- ✅ 拆分为：
  - 后台-商品管理：商品列表 + 新增/编辑商品弹窗 + 删除商品确认弹窗（3 swimlane）
  - 后台-会员管理：会员列表 + 新增/编辑会员弹窗 + 删除会员确认弹窗（3 swimlane）
  - 后台-订单管理：订单列表 + 订单详情 + 售后处理弹窗（3-4 swimlane）
  - 后台-发货单管理：发货单列表 + 发货弹窗 + 删除发货单确认弹窗（3 swimlane）
- ✅ 登录页 + 数据看板可拆为 `后台-登录页`、`后台-工作台`，或在确无歧义时保留独立小模块

**需求文档读取模式检测（必须最先执行）：**

```
检查 WORK_DIR/requirements/index.md 是否存在：
  存在 → 分拆模式（DOC_MODE = split）：
    - 读取 WORK_DIR/requirements/index.md，获取所有模块文件路径列表
    - 原型图清单来自：requirements/详细需求文档_overview.md §7
    - 全局上下文来自：requirements/详细需求文档_overview.md §2 / §2.5 / §2.8 / §3.5 / §3.6 / §4.5 / §5.5 / §5.8
    - 各模块功能细节来自：index.md 中对应模块的文件路径
  不存在 → 单文件模式（DOC_MODE = single）：
    - 所有信息来自：requirements/详细需求文档.md
```

> **分拆模式下，启动每个 subagent 前，从 index.md 查找该模块的文件路径，填入 `[需求文档读取指令]` 占位符；不得硬编码猜测文件名。**

1. 读取原型图清单（分拆模式：`requirements/详细需求文档_overview.md` §7；单文件模式：`requirements/详细需求文档.md` §7）
2. 读取全局上下文：用户角色、系统边界、模块职责、导航结构、关键业务事件、枚举值字典、权限与数据口径总则
3. 基于原型图清单和全局上下文，将页面按**业务域**功能模块分组，估算每页复杂度（简单/中等/复杂）
4. 为每个后台模块建立菜单归属和导航激活规则；为每个移动端模块建立 TabBar 归属和内页返回规则
5. **绘制页面跳转地图**：梳理所有页面间跳转关系，确保每条路径都有目标页面。发现断头路立即补充到任务清单。
6. **CRUD 完整性检查**：对任务清单中每个"列表页/管理页"，检查是否已包含以下四个关联元素。缺少任何一项立即补充到任务清单：

   | 必须存在的元素 | 说明 |
   |--------------|------|
   | 列表页（含操作列） | 筛选区 + 表格 + 分页；行操作列包含"编辑"和"删除"按钮；页面右上角有"新增"主按钮 |
   | 新增表单（页面或弹窗） | 独立页面 or 在列表页内绘制的 Modal；字段来自需求文档 |
   | 编辑表单（页面或弹窗） | 与新增相同字段，但带初始数据；通常复用同一个页面/弹窗（"新增/编辑"合并） |
   | 删除确认弹窗 | 必须是弹窗（禁止直接删除），显示被删项名称，"确认删除"（红色）+ "取消"按钮 |

   > 若需求文档明确说明使用弹窗（Modal）方式，则新增/编辑弹窗在列表页 swimlane 内绘制；若为独立页面，则单独列为任务项。

7. 读取 `SKILL_DIR/steps/step5-tasklist-format.md` 获取格式规范，输出 `原型任务清单.md` 到 `WORK_DIR/.prototype-generator/`

## 阶段 5-2：拆分生成任务

将原型页面拆分为独立任务，每个任务记录：页面名/文件名、需求文档对应章节标题、完整进出跳转关系、视觉风格。写入 `.prototype-generator/原型任务清单.md`。

8. **⚠️ CRUD 页面清单注入（必须执行，不得跳过）**：在构建每个 spec agent / subagent prompt 时，从原型任务清单中提取该模块所有含增删改操作的列表页，替换 prompt 模板中的 `[CRUD 页面清单]` 占位符。确保 agent 收到显式清单后才启动：

   ```
   本模块 CRUD 页面清单（必须为每个页面生成弹窗 swimlane）：
   - [列表页名1] → 需要：新增/编辑[对象名]弹窗 + 删除确认弹窗
   - [列表页名2] → 需要：新增/编辑[对象名]弹窗 + 删除确认弹窗
   ```

## 阶段 5-5：冒烟检查（快速质量校验）

生成导航首页之前，**必须完成以下冒烟检查**，发现问题立即修复，不得跳过。

> **Codex 特别注意：** 阶段5-5 是 Codex 主进程必须亲自执行的步骤，不得以“子任务已完成三轮精修”为由跳过。子任务内精修是模块自检，5-5 是跨模块冒烟检查，二者不可替代。

> draw.io 模式：读取 `SKILL_DIR/steps/drawio-design-rules.md` 获取输出文件规则和校验标准。

> **注意：** 深度校验（跳转标注、需求覆盖、字段 coverage、模板合规、主流程闭环等）已移入 Step 6-0 需求对照审视，此处仅做快速冒烟检查。

### 1. 文件完整性校验

- **HTML 模式**：用当前会话可用的文件列表命令扫描 `WORK_DIR/prototypes/` 目录，对比原型任务清单，列出缺失的 `.html` 文件，重新生成
- **draw.io 模式**：用当前会话可用的文件列表命令扫描 `WORK_DIR/.prototype-generator/tmp/` 下的 `drawio_*_tmp.xml` 临时文件，对比模块任务列表，列出缺失的模块临时文件，重新生成对应模块任务

### 2. 内容有效性校验（结构完整性）

逐一读取生成的文件，检查基本结构完整性：

**HTML 模式** — 每个文件必须包含：
- `<html>`、`<head>`、`<body>` 标签
- 无明显截断（文件末尾含 `</html>`）

**draw.io 模式** — 每个 `.prototype-generator/tmp/drawio_*_tmp.xml` 临时文件必须包含：
- `<diagram>` 标签（含 `id` 和 `name` 属性）
- `<mxGraphModel>` 和 `<root>` 标签
- 至少 3 个 `<mxCell>` 元素（id=0、id=1 基础层 + 至少一个 UI 元素）

发现不合格文件 → 记录并重新生成对应 Agent。

### 3. XML 合法性校验（仅 draw.io 模式）

- **未转义特殊字符检测**：用 Grep 检查 mxCell `value=""` 属性中是否含有未转义的特殊字符：
  - 搜索 `value="[^"]*&[^a-z#][^"]*"` 形式（裸 `&` 未转义为 `&amp;`）
  - 搜索 `value="[^"]*<[^/!][^"]*"` 形式（裸 `<` 未转义为 `&lt;`）
  - 发现则直接修复对应 value（替换为正确转义），不重新生成整个模块
- **swimlane parent 校验**：文件中每个 swimlane 容器（style 含 `swimlane`）都有一个 `id`（设为 `S`），其内部 UI 元素的 `parent` 必须等于 `S`，而不是 `"1"`。用 Grep 检查是否存在 `parent="1"` 的非 swimlane 元素混在 swimlane 内部——若存在，说明 subagent 未正确设置 parent，需重新生成该模块

### 4. 熔断统计

汇总所有 Agent 执行结果：
- 失败 Agent 数 ≤ 总数 50%：记录失败项，继续后续流程
- 失败 Agent 数 > 总数 50%：**立即停止**，向用户告警
