# Step 4：生成详细需求文档

> **⛔ 门禁检查：** 开始前确认 `WORK_DIR/.prototype-generator/竞品分析报告.md` 存在。不存在则**必须先回退执行 Step 3 竞品分析**，禁止跳过。

**目标：** 综合所有产品资料和竞品分析洞察，生成一份结构完整、内容详尽、有竞争力视角的增强型 PRD，既能作为原型生成的直接依据，也能为开发实现和架构判断提供稳定上游输入。

## 执行步骤

### 阶段 4-0：系统与功能列表确认（必须在生成需求文档前完成）

在撰写详细需求文档之前，**必须先向用户展示识别出的系统模块与功能列表，等待用户确认后再继续**。

1. 综合 Step 1 扫描结果、Step 2 产品定位分析、Step 3 竞品分析，梳理出：
   - 产品包含的系统模块（一级划分）
   - 每个模块下的功能列表（二级划分，每个功能一句话描述）
2. 向用户展示确认，格式如下：

```
=== 系统与功能列表确认 ===

基于产品资料和竞品调研，识别出以下系统模块与功能，请确认后继续生成详细需求文档：

📦 模块一：[模块名称]
  • [功能 1.1]：[一句话说明]
  • [功能 1.2]：[一句话说明]
  • [功能 1.3]：[一句话说明]

📦 模块二：[模块名称]
  • [功能 2.1]：[一句话说明]
  • [功能 2.2]：[一句话说明]

📦 模块三：[模块名称]
  • [功能 3.1]：[一句话说明]
  • ...

共 N 个模块，M 个功能点。

请确认：
- 回复"确认"：按以上范围生成详细需求文档
- 回复"调整 X"：指出需要修改的模块或功能（增加/删除/拆分/合并）
- 回复"重新梳理"：说明你的想法，我重新整理
```

3. **等待用户确认后**，再进入阶段 4-1 生成详细需求文档。若用户提出调整，按调整意见更新功能列表，再次展示确认，直到用户满意为止。

> ⛔ **STOP — 必须等待用户回复**
> 展示系统与功能列表后，在用户明确回复"确认"或给出调整意见之前，禁止生成需求文档。
> 不得假设用户认可当前功能列表，不得自动继续。
> **你的当前回合到此结束，等待用户输入。**

### 阶段 4-1：生成初版需求文档

> **门卫检查**：如果你尚未收到用户对阶段 4-0 系统功能列表的明确确认，立即停止并重新展示功能列表等待用户回复。

1. 参考 RountMap.md，按优先级读取所有相关资料文件
2. 读取 `竞品分析报告.md`，将竞品洞察融入需求决策（哪些功能要做、怎么做得更好）
3. 如果资料文件总内容超过 3000 行，分批读取，每批处理后记录关键信息到临时文件 `需求提炼_临时.md`
4. **判断是否进入默认强制压缩模式**：根据阶段 4-0 确认的模块数量、功能点数量、角色数、终端数，以及原型页 / swimlane 估算，满足以下任一条件即**必须**进入压缩模式：
   - 原始资料总内容 `> 3000` 行
   - 原始资料、需求草稿或合并 PRD 预计已接近 `Codex 5.4 Medium / 200K` 上下文预算
   - 模块数 `> 3`
   - 功能点数 `> 12`
   - 预计原型页面 / swimlane 数 `> 8`
   - 终端数 `> 1`
   - 关键用户角色数 `> 3`
5. **按模式输出需求文档：**
   - **未触发压缩模式**：单文件模式——创建目录 `WORK_DIR/requirements/`（如不存在），直接生成单一 `WORK_DIR/requirements/详细需求文档.md`
   - **已触发压缩模式**：读取 `SKILL_DIR/steps/step4-parallel.md`，按其流程生成 `overview + 模块详细文档 + 模块摘要 + index`（**不合并**，永久保留拆分状态，供 Step 5 / Step 6 按模块加载，显著减少上下文）

> **估算规则：** 页面 / swimlane 数优先根据原型图清单草案、系统模块确认结果和 CRUD 闭环推导，采用保守估算；一旦难以确定，默认按更复杂场景处理并进入压缩模式。
> **200K 预算规则：** 对 Codex 5.4 Medium，不能把 200K 当作可读满额。Step 4 必须默认预留 `30%~40%` 给推理、工具输出和回修，因此只要判断“单文件 PRD + 必要上下文”可能逼近预算，就必须改走 `overview + module_brief + detail + index`。

文档格式规范：读取 `SKILL_DIR/steps/step4-doc-format.md` 获取完整的章节结构和字段要求。

**🚫 强制规则：压缩模式不是建议，是正式门禁**

- 已触发压缩模式时，不得继续生成单一合并大 PRD 作为 Step 5 主输入
- 已触发压缩模式时，必须生成：
  - `requirements/详细需求文档_overview.md`
  - `requirements/module_briefs/模块摘要_[模块中文名].md`
  - `requirements/index.md`
  - `requirements/详细需求文档_[模块中文名].md`
- Step 5 / Step 6 分拆模式的默认读取顺序必须是：`index.md -> overview -> module_brief -> 模块详细文档 -> page_spec`
- 未生成 `module_brief` 时，禁止启动 Step 5 子 agent
- 面向 Codex 5.4 Medium 时，单个模块摘要应优先压缩到“一页内可读”；若某模块详细文档仍过长，必须继续拆章节索引，而不是要求后续子任务整篇通读

**🚫 强制规则：需求文档不是 API 文档或 DDL，但必须具备开发和架构可消费的最小信息**

- overview 必须覆盖：
  - `§2.5 系统边界与外部依赖`
  - `§2.8 模块职责与协作关系`
  - `§3.5 移动端导航结构`（有移动端时）
  - `§3.6 后台导航结构`（有后台 Web/Admin 时）
  - `§4.5 关键业务事件`
  - `§5.8 权限与数据口径总则`
- 每个功能点必须新增 3 个固定区块：
  - `▌ 开发关注点`
  - `▌ 权限与可见范围`
  - `▌ 数据影响`
- 以上区块用于支撑后续开发、架构和原型生成，不要求在 Step 4 中直接展开完整 REST 接口、错误码清单或建表 SQL；这些内容应由后续专门 skill 派生。

**🚫 强制规则：每个功能点必须包含字段规格，否则视为输出未完成**

每写完一个功能点的"功能描述/用户故事"后，**必须立即追加对应的字段规格区块，不得跳过**。写完一个功能点后执行自查：

> **自查拦截：** 检查该功能点是否存在以下区块（根据页面类型选择）：
> - 所有功能点 → 必须有 `▌ 开发关注点`、`▌ 权限与可见范围`、`▌ 数据影响`
> - 有列表页 → 必须有 `▌ 列表/查询页字段规格`，含筛选条件、表格列定义、分页规则
> - 有表单页 → 必须有 `▌ 新增/编辑表单字段规格`，含逐字段规格表和业务规则
> - 有详情页 → 必须有 `▌ 详情/状态页字段规格`，含展示字段、状态流转、操作按钮
> - 列表页、详情页、表单提交页 → 必须有 `▌ 三态设计` 表格（空态 / 加载态 / 错误态），登录页和弹窗可简写
>
> **缺少任何一个对应区块 → 停止继续下一个功能点，先补全当前功能点的字段规格。**

字段规格要求如下：

- **开发关注点**：
  - 必须写清校验、幂等/防重复提交、失败处理、日志/审计要求
  - 若涉及外部系统，必须写清失败后的业务影响和回滚/重试口径

- **权限与可见范围**：
  - 必须写清页面可见角色、关键按钮权限、数据范围限制、越权处理方式
  - 不能只写“管理员可见”这种泛化表述，必须指出是否按部门/组织/角色/门店过滤

- **数据影响**：
  - 必须写清读取/新增/修改哪些实体
  - 必须说明保存或操作成功后，会影响哪些列表、详情、统计、消息、日志或外部系统

- **列表/查询页**：
  - 逐条列出筛选条件（含控件类型：关键词/下拉/日期范围、枚举值、数据来源）
  - 逐列列出表格展示列（含是否可排序、特殊展示说明，如脱敏、Tag颜色、操作列按钮）
  - 写明分页业务规则（默认条数、默认排序字段、最大返回条数等）
  - 补充导出范围、批量操作规则、按钮前置条件

- **新增/编辑表单页**：
  - 逐字段列出（字段名 | 控件类型 | 是否必填 | 校验规则 | 占位提示）
  - 校验规则要具体：字符长度范围、格式（如手机号格式 1[3-9]XXXXXXXXX）、唯一性约束
  - 写明表单业务规则（如：编辑时某字段不可修改；提交后的页面跳转行为）
  - 补充字段来源、编辑权限、提交副作用

- **详情页**：
  - 列出所有展示字段
  - 写明状态流转链（状态A → 操作 → 状态B → 操作 → 状态C）
  - 列出各状态下可用的操作按钮
  - 补充关键异常态和跨模块联动影响

> 字段规格是 Step 5 subagent 绘制原型的直接依据。缺少字段规格会导致原型字段用"字段一/字段二"序号占位或遗漏关键字段；缺少开发关注点、权限与数据影响会导致后续实现、架构和高保真原型对同一功能做出相互矛盾的假设。

### 阶段 4-2：功能完整性检查与自动补全

初版需求文档生成后，对每个功能模块进行"关联功能依赖分析"，检查是否存在功能缺口。

#### 检查规则

对每个功能模块，套用以下依赖模型逐一排查：

| 如果存在这个功能 | 必须同时存在的关联功能 |
|---------------|-------------------|
| 角色管理 | 人员管理、人员与角色绑定、角色权限配置、权限资源管理 |
| 用户注册/登录 | 找回密码、账号注销、登录日志、多端登录管理 |
| 内容发布 | 内容草稿、内容审核、内容下架、内容版本历史 |
| 订单管理 | 订单创建、订单取消、退款退货、订单状态流转、订单详情 |
| 支付功能 | 支付成功/失败回调、支付记录查询、退款流程 |
| 消息通知 | 通知列表、已读/未读状态、通知设置（哪些推送） |
| 数据报表 | 数据筛选、数据导出、时间范围选择 |
| 文件上传 | 文件列表管理、文件删除、文件预览、上传进度 |
| 搜索功能 | 搜索历史、搜索结果为空时的引导、搜索建议 |
| 商品管理 | 商品分类管理、商品上下架、库存管理、商品详情 |

> 以上为通用规则，还需结合产品具体业务场景进行判断。

#### 检查流程

1. 遍历需求文档中每个功能模块，对照上方依赖模型，列出所有发现的功能缺口
2. 对每个缺口判断：
   - **资料中有提及但未展开**：直接补充完整需求
   - **资料中完全没有**：调研同类产品该功能的最佳实践，再补充需求
3. 将所有补全的功能整理为"功能补全清单"，**向用户展示**：

```
=== 功能完整性检查结果 ===

发现以下功能缺口，已自动补全：

✅ 已补全（资料中有线索）：
1. 人员管理 — 原资料仅提角色管理，已补充人员列表、人员新增/编辑/删除、人员状态管理
2. ...

🔍 已调研补全（资料中无提及，基于行业实践）：
1. 角色权限配置 — 参考 [竞品名] 的权限树设计，补充菜单权限、操作权限、数据权限三级结构
2. ...

⚠️ 建议关注但暂未补全（需您确认是否纳入）：
1. 多租户隔离 — 是否需要支持多租户？如需要，权限体系需重新设计
2. ...

是否接受以上补全？
- 回复"全部接受"：按补全后的需求继续
- 回复"接受1,2，跳过3"：选择性接受
- 回复"全部跳过"：保持原需求继续
```

> ⛔ **STOP — 必须等待用户回复**
> 展示功能补全清单后，在用户明确回复之前，禁止更新需求文档。
> **你的当前回合到此结束，等待用户输入。**

4. 等待用户确认后，将接受的补全内容写入 `requirements/详细需求文档.md`，更新"原型图清单"章节，追加"功能补全记录"章节

```markdown
## 8. 功能补全记录

| 补全功能 | 补全原因 | 来源 | 影响模块 |
|---------|---------|------|---------|
| 人员管理 | 角色管理的必要关联功能 | 逻辑推导 | 权限管理模块 |
| 角色权限配置 | 行业标配，资料未提及 | 在线调研 | 权限管理模块 |
```

> **质量标准：**
> - 每个功能点须有清晰验收标准，竞品参考应指明本产品改进方向而非照抄
> - 原型图清单（§7）每行必须填写「页面类型」「页面原型类型」「是否主导航页」「导航归属」「主要字段数量」「业务规则展示重点」六项，供 Step 5 Agent 评估页面复杂度、导航归属和规则展示方式
> - 枚举值字典（§5.5）必须覆盖需求文档中所有状态类字段，供原型 Agent 生成 Tag 颜色和下拉选项时引用
> - 有后台 Web/Admin 时，需求文档必须明确后台导航结构；否则 Step 5 不得自行猜测左侧菜单
> - Step 4 产物应达到“增强 PRD”标准：能直接驱动原型生成，同时为后续 API 设计和数据模型设计提供稳定输入，但不在本阶段直接展开完整接口和 DDL
> - 文档格式详见 `SKILL_DIR/steps/step4-doc-format.md`
