# Step 6：需求对照审视 + 改进建议迭代

## 阶段 6-0：需求对照审视（强制，不可跳过）

> 目标：逐页对照需求文档、`.prototype-generator/原型任务清单.md`、`.prototype-generator/page_specs/` 与最终原型，执行预处理校验 + 七个维度审视，输出审视报告并等待用户确认后修复。

### 预处理：跳转与覆盖率校验

> 以下校验项从 Step 5-5 移入，作为深度审视的一部分执行。

**加载验收规则：**
- 通用：读取 `SKILL_DIR/steps/acceptance-rules-A.md`（A3 主操作 / A4 状态 / A5 主流程闭环）
- 通用：读取 `SKILL_DIR/steps/acceptance-rules-C.md`（C1-C4 反模式检测）
- draw.io 模式追加：读取 `SKILL_DIR/steps/acceptance-rules-B.md`（B1-B4 模板验收）

**1. 跳转标注校验**
- HTML 模式：逐一读取所有 HTML 文件，提取 href/onclick 跳转目标，检查目标文件是否存在，修复断链
- draw.io 模式：逐一读取 .drawio 文件中所有 diagram，提取 tooltip 中跳转目标，检查是否在任务清单中存在；汇总跨模块跳转，对照导航 diagram 连线补充缺失

**2. 需求覆盖校验**
- 对照原型图清单（分拆模式：overview §7；单文件模式：详细需求文档 §7），确认每行对应文件已生成

**3. draw.io 专项检测（脚本自动化）**

先运行自动验收脚本：

```bash
python3 SKILL_DIR/scripts/validate.py WORK_DIR/prototypes/[产品名称].drawio --fix
```

> 脚本自动完成：C1 说明框 / C2 大段文字 / C3 页面文档化 / C4 视觉层级 / C5 坐标对齐（--fix 自动修复） / C6 登录页导航 / C7 XML 合法性 / C8 数据行充分性。
> 输出报告中 FAIL/WARN 项需要人工复查和修复。

然后补充脚本无法覆盖的人工检测：
- 禁止内容检测：Grep 搜索 `关键规则`/`验收线`/`开发注意`/`测试用例`/`TODO`/`待定`/`待补充`
- 尺寸合规抽查：检查按钮/输入框 height 是否在 32-56px，表格行高是否在 44-56px

### 七维度审视

> **⚡ 并行执行：** 维度 1-5 互相独立，必须并行执行，但**任一时刻最多只运行 3 个子 agent**。因此维度 1-5 需分两批执行：先启动 3 个，再启动剩余 2 个。Codex 中用多个 `spawn_agent`；Claude Code 中用多个 `Agent`。维度 6（主流程闭环）和维度 7（模板合规）依赖前 5 个维度的修复结果，需等待 1-5 全部完成后再顺序执行。
>
> ```
> # 第一批并行启动 3 个 Agent
> Agent(prompt="审视维度一：界面完整性...", run_in_background=True)
> Agent(prompt="审视维度二：字段/元素完整性...", run_in_background=True)
> Agent(prompt="审视维度三：排版/视觉合理性...", run_in_background=True)
> # 等第一批完成后，启动第二批
> Agent(prompt="审视维度四：内容真实性...", run_in_background=True)
> Agent(prompt="审视维度五：视觉结构...", run_in_background=True)
> # 等待全部完成后，顺序执行维度 6、7
> ```
>
> Codex 等价做法：
>
> ```
> spawn_agent(agent_type="worker", message="审视维度一：界面完整性...")
> spawn_agent(agent_type="worker", message="审视维度二：字段/元素完整性...")
> spawn_agent(agent_type="worker", message="审视维度三：排版/视觉合理性...")
> # wait 第一批完成后，再启动第二批
> spawn_agent(agent_type="worker", message="审视维度四：内容真实性...")
> spawn_agent(agent_type="worker", message="审视维度五：视觉结构...")
> # 等第二批完成后，再顺序执行维度 6、7
> ```
>
> 每个子任务的 prompt 需包含：WORK_DIR 路径、OUTPUT_FORMAT、需求文档路径、验收规则文件路径、该维度的完整检查方法。发现问题后直接修复文件并输出修复报告。

**维度一：界面完整性**

对照"原型图清单"中每一行，逐一确认对应界面是否已生成：
- HTML 模式：对应 `.html` 文件是否存在
- draw.io 模式：对应 swimlane 是否在某个 diagram 中存在
- 记录所有缺失页面

**维度二：字段/元素完整性**（逐页检查）

对每个已生成页面，读取其内容，对照需求文档中该页面的字段列表/功能描述，检查：
- 必填字段是否全部存在（如表单的每个输入项）
- 关键操作按钮是否存在（如提交、取消、查看、编辑、删除）
- 列表页的列标题是否完整（是否缺少某列）
- 状态标签/枚举值是否体现（如订单状态、商品分类）
- 关键提示文案是否有（如空态引导语、错误提示位置）
- **空态覆盖**：列表页、首页、Dashboard 类页面是否有空态展示（无数据时的引导文案 + 引导操作按钮）；缺失则标记
- **异常态覆盖**：核心页面（列表、详情、表单提交）是否有异常态展示（加载失败/网络错误提示 + 重试按钮）；缺失则标记
- **处理中态**：表单提交、支付等关键操作是否有处理中态（按钮 disabled + 文字变"处理中..."）；缺失则标记

**主操作 coverage（A3）：** 按 acceptance-rules-A.md 中 A3 检查方法，逐页对照需求文档中的核心操作按钮，输出 coverage 报告，缺失的直接补充。

**状态 coverage（A4）：** 按 acceptance-rules-A.md 中 A4 检查方法，检查列表页是否展示 ≥2 种状态、详情页是否有状态标注，输出覆盖率，< 80% 必须修复。

**字段 coverage（逐页强制执行）：**
逐页对照需求文档字段规格：
- 列表页：筛选条件 + 列表展示列名
- 表单页：表单字段名（含控件类型、是否必填）
- 详情页：展示字段名
输出 coverage 报告，< 80% 的页面必须修复。修复方式：统一先修改 `.prototype-generator/page_specs/page_spec_*.md`，再重跑对应模块渲染。

**维度三：排版合理性**

- **通用**：页面是否有清晰的视觉主次层级，主操作是否突出
- **HTML 模式**：导航/标题/内容/操作按钮区域划分是否清晰；是否有未对齐的组件
- **draw.io 模式**：UI 区内是否混入了标注文字；标注区是否有内容越界进入 UI 区；同一模块页面 swimlane 宽高是否一致
- **骨架隔离检查**（通用）：登录页、注册页、错误页、支付结果页等独立页面，是否错误包含了侧边栏、顶部业务导航或面包屑；发现则标记为排版错误
- **多模式互斥检查**（通用）：需求中含"支持 X 和 Y 两种方式"的页面，是否将两种方式字段同时平铺展示（而非 Tab 切换）；发现则标记为布局错误

**维度四：内容真实性**

逐页检查，发现以下任意情况标记为内容错误：
- 出现占位文字：`功能待定`、`这里是内容`、`示例文字`、`文字N`、`按钮N`、`Lorem ipsum`、`待补充`、`暂无`（无引导操作时）
- 表格数据行使用`数据1/数据2`、`张三/李四`（虚构姓名可接受，但字段值不能是序号）
- 字段 label 使用`字段1`、`输入框A`等非业务名称

**维度五：视觉结构（规则 B3/C1/C2/C3/C4）**

按 `acceptance-rules-B.md` 中 B3 和 `acceptance-rules-C.md` 中 C 类规则逐页检查：

- **B3 主区突出**：计算主内容区面积占比（表格区/字段卡片/键值对区），占比 < 30% 标记为主区不突出
- **C1 说明框过多**：UI 区内纯文字说明元素（value > 30 字符的 text 元素，非 label/title）≥ 5 个 → 标记
- **C2 大段文字占主体**：UI 区内单个 mxCell value > 80 字符（标注区除外）→ 标记
- **C3 页面像文档/PPT**：统计交互组件占比（input/btn/select/tag），交互组件 < 10% 或文字组件 > 70% → 标记为"像文档"
- **C4 内容同权**：检查按钮是否只有一种样式（全是 btn_primary），字号是否只有一种 → 标记为"无视觉层级"

**维度六：主流程闭环复核（规则 A5）**

复核预处理阶段的跳转标注校验结果，重点检查修复后是否引入新的断点：
- 补充的按钮是否有正确的 tooltip/href 跳转目标
- 补充的页面是否能从其他页面到达
- 操作成功/失败后是否有反馈（Toast/错误提示）

**主流程闭环完整校验（A5）：** 按 acceptance-rules-A.md 中 A5 检查方法，读取需求文档「核心业务流程」，逐条验证跳转链路可达性，覆盖 CRUD 闭环、查看闭环、登录闭环。输出闭环校验结果，缺失跳转立即修复。

**维度七：模板合规（仅 draw.io 模式，规则 B1/B2/B4）**

按 `acceptance-rules-B.md` 中 B 类规则执行：
- B1 页面类型校验：对照需求文档确认 page_spec 类型标注正确
- B2 骨架完整性校验：逐页统计骨架必备元素，输出完整度百分比
- B4 布局顺序校验：按 y 坐标排列所有元素，检查顺序是否符合模板定义
不通过 → 修改 page_spec 后重新渲染。

### draw.io 模式：HTML 对比（按需触发）

> **draw.io 模式下，HTML 对比仅在以下条件满足时触发，不再强制对所有页面执行：**
>
> **触发条件（满足任一即触发）：**
> 1. 七维度审视中维度二（字段/元素完整性）发现评级为 ❌ 的页面
> 2. 字段 coverage < 60% 的页面（严重缺失，需交叉验证）
> 3. 用户主动要求对比的页面
>
> **快捷路径（优先使用）：** 如果存在 `page_specs/page_spec_*.md`（两阶段模式），优先用 page_spec vs 需求文档做结构化字段 diff，只有 diff 无法确认的差异才生成 HTML 对比稿。
>
> 七维度审视完成后，对触发条件命中的页面执行 HTML 对比。

触发时执行以下流程：

**Step A：生成对比用 HTML 临时稿**

为存疑页面生成轻量 HTML 版本，保存到 `WORK_DIR/review_tmp/[页面名].html`：
- 读取 `SKILL_DIR/steps/html-spec.md` 获取 HTML 规范
- 基于需求文档同一章节生成该页面的 HTML 版本
- 输出只需覆盖核心功能，不追求完整交互效果
- 禁止在控制台输出 HTML 正文，只输出：`✅ 对比稿 [页面名].html 生成完毕`

**Step B：对比差异，列出 draw.io 问题清单**

逐项对比 HTML 稿与 draw.io 对应 swimlane，记录差异：

```
=== [页面名] HTML vs draw.io 对比 ===

字段/元素差异：
  ✅ [字段名]：两者一致
  ❌ [字段名]：HTML 有，draw.io 缺失
  ❌ [字段名]：HTML 有，draw.io 缺失

排版差异：
  ⚠️ HTML 中 [区域A] 在顶部导航下方，draw.io 中位置偏移约 [N]px
  ⚠️ HTML 中按钮组水平排列，draw.io 中为垂直堆叠

结论：draw.io 需修正 X 处
```

**Step C：以 HTML 稿为参照修正 draw.io**

按对比清单，精确修改 `[产品名称].drawio` 对应 swimlane：
- 补充缺失的 `<mxCell>` 元素（字段/按钮），坐标参照 HTML 布局折算
- 调整位置偏差的组件坐标
- 修复排版结构（水平/垂直排列、对齐方式）

**Step D：清理临时文件**

修复完成后删除 `WORK_DIR/review_tmp/` 目录下本次生成的所有 HTML 临时稿。

### 执行修复（常规问题）

用户确认后，逐项修复。**draw.io 模式修复优先级：先修改 page_spec → 再重跑渲染模块（禁止直接 patch XML，除非是微小坐标调整）**：

- **缺失页面**：参照 Step 5 agent prompt 模板，单独启动 Agent 生成该页面；draw.io 模式先在 page_spec 中补充对应 swimlane，再重跑渲染 Agent，最后追加到 `.drawio` 文件
- **缺失字段/按钮**：统一先修改对应 `page_specs/page_spec_*.md`，再重跑该模块渲染；禁止把最终 HTML 当主修复面
- **排版/坐标问题**：draw.io 模式：修改 page_spec 中对应元素的 x/y/width/height → 重跑渲染；HTML 模式：修改 page_spec 中布局说明后重渲染；draw.io 若只是 1-2 个元素的微调（< 3 个 mxCell），可直接微调 `.drawio` XML
- 每次修复后更新 `执行状态.md` 的"Spec 版本记录"表格，记录版本号、变更原因和修改摘要

修复完成后，将审视结果追加到 `WORK_DIR/.prototype-generator/执行状态.md` 的 Step 6 迭代记录：

```
| 审视轮 | 发现 X 处问题，HTML对比 Y 页，已修复 Z 处 |
```

## 阶段 6-1：自评与建议生成

> **🚫 强制一轮迭代规则：原型初次完成后必须自动执行第 1 轮迭代，不得询问用户是否需要改进，直接生成建议并执行改进。第 2 轮起转为可选模式，等待用户指令。**

完成所有原型后，从以下维度审视已生成的原型，列出 **3-5 条具体的改进建议**：

**审视维度：**
- **流程完整性**：是否有用户路径无法走通？是否有功能模块缺少关键状态（如加载失败、权限不足）？
- **交互细节**：是否有可以更流畅的过渡动效？表单校验是否足够友好？
- **内容真实性**：示例数据是否贴近真实业务场景？空状态是否有引导文案？
- **竞品对标**：竞品分析报告中提到的差异化亮点是否都在原型中体现？
- **边缘场景**：错误页、超时页、无权限页等异常状态是否覆盖？

**建议格式：**

```
=== 原型改进建议（第 N / 4 轮）===
[第 1 轮附注：强制迭代轮，自动执行所有改进项]

我在审视生成的原型后，发现以下可以进一步完善的方向：

1. [建议标题]
   问题：[当前原型的不足之处]
   改进：[具体怎么改]
   影响页面：[HTML模式：哪些.html文件 / draw.io模式：哪个diagram的哪个swimlane]

2. [建议标题]
   ...
```

## 阶段 6-2：执行改进

**第 1 轮（强制迭代）：**
- 无需等待用户确认，列出建议后**立即自动执行全部改进项**
- 改进完成后输出本轮摘要，进入下一轮

**第 2 轮起（可选迭代）：**
- 列出改进建议后，等待用户选择：

```
=== 原型改进建议（第 N / 4 轮）===

...建议列表...

是否需要继续改进？请告诉我：
- 回复"全部改"：按照以上所有建议改进
- 回复"改1,3"（数字）：只改指定建议
- 回复"不用了"：结束，保持现状
- 或者直接描述你有其他想法
```

**执行步骤（每轮共用）：**

1. 对每个改进项，直接编辑对应的文件
2. 如果改进引入了新的需求决策，同步更新 `requirements/详细需求文档.md`
3. 在 `WORK_DIR/.prototype-generator/执行状态.md` 的"Step 6 迭代记录"中追加本轮摘要（轮次 + 改进内容摘要）
4. 当前迭代轮次 < 上限时，**再次进入阶段 6-1**，生成新一轮改进建议

**迭代上限：最多 4 轮**

**循环终止条件（满足任意一条即终止）：**
- 已完成强制一轮，且用户明确表示满意（回复"不用了"/"好了"/"完成"等）
- 连续两轮建议都没有实质性改进点（第 2 轮后）
- 用户主动中止（第 2 轮后）
- **已达到第 4 轮上限**：主动告知用户并停止循环：

```
已完成第 4 轮改进（迭代上限）。
如需继续优化，请重新触发 Step 6，或在下次会话中继续。
```

将 `执行状态.md` 整体状态更新为"已完成"。

> **改进原则：** 每轮改进要聚焦、可执行，不要提出过于笼统的建议（如"整体优化一下"）。每条建议应指向具体页面的具体问题，让用户能快速判断是否值得改。
