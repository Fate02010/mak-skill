# Step 6：需求对照审视 + 改进建议迭代

所有原型图生成完毕后，**先强制执行需求对照审视（阶段 6-0），再进入改进建议环节**。

---

## 阶段 6-0：需求对照审视（强制，不可跳过）

> 目标：逐页对照需求文档与原始资料，检查界面缺失、字段元素缺失、排版合理性三个维度，输出审视报告并等待用户确认后修复。

### 准备工作

1. 读取 `WORK_DIR/详细需求文档.md`，提取"原型图清单"和每个页面的功能描述、字段列表
2. 读取 `WORK_DIR/原型任务清单.md`，获取已生成的页面列表
3. 扫描已生成文件：
   - **HTML 模式**：`Glob WORK_DIR/prototypes/*.html`
   - **draw.io 模式**：读取 `WORK_DIR/prototypes/[产品名称].drawio`，列出所有 `<diagram name>` 和 swimlane

### 三维度审视

**维度一：界面完整性**

对照"原型图清单"中每一行，逐一确认对应界面是否已生成：
- HTML 模式：对应 `.html` 文件是否存在
- draw.io 模式：对应 swimlane 是否在某个 diagram 中存在
- 记录所有缺失页面

**维度二：字段/元素完整性**（逐页检查）

对每个已生成页面，读取其内容，对照需求文档中该页面的字段列表/功能描述，检查：
- 必填字段是否全部存在（如表单的每个输入项）
- 关键操作按钮是否存在（如提交、取消、查看、编辑、删除）
- 列表页的列标题是否完整（是否缺少某列）
- 状态标签/枚举值是否体现（如订单状态、商品分类）
- 关键提示文案是否有（如空态引导语、错误提示位置）

**维度三：排版合理性**

- **通用**：页面是否有清晰的视觉主次层级，主操作是否突出
- **HTML 模式**：导航/标题/内容/操作按钮区域划分是否清晰；是否有未对齐的组件
- **draw.io 模式**：UI 区内是否混入了标注文字；标注区是否有内容越界进入 UI 区；同一模块页面 swimlane 宽高是否一致

### 输出审视报告

```
=== 原型需求对照审视报告 ===

【维度一：界面完整性】
✅ 所有 N 个页面均已生成
⚠️ 缺失页面（M 个）：
  - [页面名]（需求文档章节：§X.X）
  - [页面名]（需求文档章节：§X.X）

【维度二：字段/元素完整性】
✅ [页面名]：字段完整
⚠️ [页面名]：缺失以下元素
  - [字段名/按钮名]（需求文档 §X.X 要求）
  - [字段名/按钮名]
⚠️ [页面名]：缺失以下元素
  - ...

【维度三：排版合理性】
✅ 整体布局合理
⚠️ [页面名]：[问题描述，如"标注文字覆盖了输入框区域"]
⚠️ [页面名]：[问题描述，如"删除按钮缺少危险色标注"]

=== 发现问题共 X 处，建议修复 ===
是否立即修复？（"全部修复" / "修复1,3" / "跳过进入改进建议"）
```

### draw.io 模式：HTML 对比辅助机制

> **触发条件：** 审视 draw.io 原型时，遇到以下任意情况，自动触发 HTML 对比：
> - 字段/元素完整性存疑（draw.io XML 密集，难以逐一核实）
> - 排版合理性有疑问（坐标数字难以直观判断布局是否合理）
> - 某页面问题标注超过 3 处（说明该页面整体质量存疑）

触发时执行以下流程：

**Step A：生成对比用 HTML 临时稿**

为存疑页面生成轻量 HTML 版本，保存到 `WORK_DIR/review_tmp/[页面名].html`：
- 读取 `SKILL_DIR/steps/html-spec.md` 获取 HTML 规范
- 基于需求文档同一章节生成该页面的 HTML 版本
- 输出只需覆盖核心功能，不追求完整交互效果
- 禁止在控制台输出 HTML 正文，只输出：`✅ 对比稿 [页面名].html 生成完毕`

**Step B：对比差异，列出 draw.io 问题清单**

逐项对比 HTML 稿与 draw.io 对应 swimlane，记录差异：

```
=== [页面名] HTML vs draw.io 对比 ===

字段/元素差异：
  ✅ [字段名]：两者一致
  ❌ [字段名]：HTML 有，draw.io 缺失
  ❌ [字段名]：HTML 有，draw.io 缺失

排版差异：
  ⚠️ HTML 中 [区域A] 在顶部导航下方，draw.io 中位置偏移约 [N]px
  ⚠️ HTML 中按钮组水平排列，draw.io 中为垂直堆叠

结论：draw.io 需修正 X 处
```

**Step C：以 HTML 稿为参照修正 draw.io**

按对比清单，用 `Edit` 工具精确修改 `[产品名称].drawio` 对应 swimlane：
- 补充缺失的 `<mxCell>` 元素（字段/按钮），坐标参照 HTML 布局折算
- 调整位置偏差的组件坐标
- 修复排版结构（水平/垂直排列、对齐方式）

**Step D：清理临时文件**

修复完成后删除 `WORK_DIR/review_tmp/` 目录下本次生成的所有 HTML 临时稿。

---

### 执行修复（常规问题）

用户确认后，逐项修复：
- **缺失页面**：参照 Step 5 agent prompt 模板，单独启动 Agent 生成该页面，draw.io 模式追加到 `.drawio` 文件
- **缺失字段/按钮**：用 `Edit` 工具直接修改对应文件，补充缺失元素
- **排版问题**：用 `Edit` 工具修正坐标/样式/分区；存疑时触发上方 HTML 对比机制

修复完成后，将审视结果追加到 `WORK_DIR/执行状态.md` 的 Step 6 迭代记录：

```
| 审视轮 | 发现 X 处问题，HTML对比 Y 页，已修复 Z 处 |
```

## 阶段 6-1：自评与建议生成

完成所有原型后，从以下维度审视已生成的原型，列出 **3-5 条具体的改进建议**：

**审视维度：**
- **流程完整性**：是否有用户路径无法走通？是否有功能模块缺少关键状态（如加载失败、权限不足）？
- **交互细节**：是否有可以更流畅的过渡动效？表单校验是否足够友好？
- **内容真实性**：示例数据是否贴近真实业务场景？空状态是否有引导文案？
- **竞品对标**：竞品分析报告中提到的差异化亮点是否都在原型中体现？
- **边缘场景**：错误页、超时页、无权限页等异常状态是否覆盖？

**建议格式：**

```
=== 原型改进建议 ===

我在审视生成的原型后，发现以下可以进一步完善的方向：

1. [建议标题]
   问题：[当前原型的不足之处]
   改进：[具体怎么改]
   影响页面：[HTML模式：哪些.html文件 / draw.io模式：哪个diagram的哪个swimlane]

2. [建议标题]
   ...

是否需要继续改进？请告诉我：
- 回复"全部改"：按照以上所有建议改进
- 回复"改1,3"（数字）：只改指定建议
- 回复"不用了"：结束，保持现状
- 或者直接描述你有其他想法
```

## 阶段 6-2：执行改进

用户确认改进后：

1. 根据用户选择，确定要改进的建议列表
2. 对每个改进项，直接编辑对应的文件
3. 如果改进引入了新的需求决策，同步更新 `详细需求文档.md`
4. 在 `WORK_DIR/执行状态.md` 的"Step 6 迭代记录"中追加本轮摘要（轮次 + 改进内容摘要）
5. 当前迭代轮次 < 上限时，**再次进入阶段 6-1**，生成新一轮改进建议

**迭代上限：最多 5 轮**

每次进入阶段 6-1 时，在建议标题前显示当前轮次：

```
=== 原型改进建议（第 N / 5 轮）===
```

**循环终止条件（满足任意一条即终止）：**
- 用户明确表示满意（回复"不用了"/"好了"/"完成"等）
- 连续两轮建议都没有实质性改进点
- 用户主动中止
- **已达到第 5 轮上限**：主动告知用户并停止循环：

```
已完成第 5 轮改进（迭代上限）。
如需继续优化，请重新触发 Step 6，或在下次会话中继续。
```

将 `执行状态.md` 整体状态更新为"已完成"。

> **改进原则：** 每轮改进要聚焦、可执行，不要提出过于笼统的建议（如"整体优化一下"）。每条建议应指向具体页面的具体问题，让用户能快速判断是否值得改。
