# 原型验收规则

本文件定义三类验收规则，在 Step 5-5（强制自查）和 Step 6-0（需求对照审视）中引用执行。
每条规则标注检查方法（手动读取 / Grep 自动检测）和不通过时的修复方式。

---

## A 类：覆盖率验收（增强项）

> A1（页面齐）、A2（字段齐）已有规则覆盖，以下为新增的 A3–A5。

### A3 — 主操作是否齐

**定义：** 需求文档中每个页面描述的核心操作按钮，必须在原型中存在对应的可交互元素。

**检查方法：**

1. 读取 `requirements/详细需求文档.md`，对每个页面提取「关键交互」列和「操作按钮」描述
2. 逐页对照原型文件中的按钮元素：
   - **HTML 模式**：Grep 搜索 `<button` 和 `onclick`，提取按钮文案
   - **draw.io 模式**：Grep 搜索 style 含 `fillColor=#1e88e5`（主按钮）和 `fillColor=#ffffff;strokeColor=#1e88e5`（次要按钮）的 mxCell，提取 value
3. 将需求文档中的操作列表与原型中的按钮列表做差集

**输出格式：**
```
[页面名] 主操作校验：
  ✅ 新增 | ✅ 编辑 | ✅ 删除 | ❌ 导出（缺失）| ❌ 批量审核（缺失）
```

**不通过修复：** 用 Edit 在对应页面补充缺失的操作按钮（含 tooltip 跳转标注）。

---

### A4 — 状态是否齐

**定义：** 需求文档中定义的状态枚举值，必须在原型中通过 Tag 组件或状态流转说明体现。

**检查方法：**

1. 读取 `requirements/详细需求文档.md`，提取每个功能模块的状态枚举（如「待支付/已支付/已发货/已完成/已取消」）
2. 逐页对照原型文件中的状态展示：
   - **HTML 模式**：Grep 搜索 `class="tag"` 或 `class="status"` 相关元素的文案
   - **draw.io 模式**：Grep 搜索 style 含 `fillColor=#e8f5e9`（成功）/`fillColor=#fff8e1`（警告）/`fillColor=#ffebee`（错误）/`fillColor=#e3f2fd`（信息）的 mxCell value
3. 检查项：
   - 列表页表格：是否有状态列，且至少展示了 2 种不同状态的示例数据行
   - 详情页：是否有当前状态 Tag + 状态流转说明（在标注区）
   - 标注区：是否列出了完整的状态枚举值

**输出格式：**
```
[模块名] 状态校验：
  需求定义：待支付/已支付/已发货/已完成/已取消（共 5 种）
  列表页展示：✅ 待支付 | ✅ 已发货 | ❌ 已完成（表格中未出现）
  详情页标注：✅ 完整状态流转已标注
  状态覆盖率：3/5 = 60%
```

**不通过修复：**
- 列表页数据行补充缺失状态的示例行（替换现有重复状态的行）
- 详情页标注区补充状态流转说明
- 状态覆盖率要求 ≥ 80%

### A5 — 主流程是否闭环

**定义：** 用户的核心业务路径必须能从入口走通到终点，不存在"进得去出不来"或"操作后无反馈"的断点。

**检查方法：**

1. 读取 `requirements/详细需求文档.md` 的「核心业务流程」章节，提取每条主流程的步骤链
2. 对每条流程逐步验证跳转可达性：

```
示例流程：商品列表 → 点击新增 → 填写表单 → 提交 → 返回列表（刷新）
检查链路：
  ✅ 商品列表有"新增"按钮（href/tooltip → 新增页）
  ✅ 新增页有"提交"按钮（href/tooltip → 列表页）
  ✅ 新增页有"取消"按钮（href/tooltip → 列表页）
  ❌ 提交成功后无 Toast/提示反馈
```

3. 必须覆盖的闭环路径：
   - **CRUD 闭环**：列表 → 新增 → 提交 → 回列表；列表 → 编辑 → 提交 → 回列表；列表 → 删除 → 确认 → 回列表
   - **查看闭环**：列表 → 详情 → 返回列表
   - **登录闭环**：登录页 → 登录成功 → 首页；登录失败 → 错误提示（停留登录页）

**输出格式：**
```
=== 主流程闭环校验 ===

流程1：[下单流程]
  商品列表 →(点击商品)→ 商品详情 ✅
  商品详情 →(加入购物车)→ 购物车 ✅
  购物车 →(去结算)→ 下单页 ✅
  下单页 →(提交订单)→ 支付页 ✅
  支付页 →(支付成功)→ 订单详情 ✅
  闭环：✅ 完整

流程2：[用户管理 CRUD]
  用户列表 →(新增)→ 新增弹窗 ✅
  新增弹窗 →(提交)→ 用户列表 ✅
  用户列表 →(编辑)→ 编辑弹窗 ✅
  编辑弹窗 →(提交)→ 用户列表 ✅
  用户列表 →(删除)→ 删除确认弹窗 ✅
  删除确认弹窗 →(确认)→ 用户列表 ✅
  闭环：✅ 完整

流程3：[登录]
  登录页 →(登录成功)→ 首页 ✅
  登录页 →(登录失败)→ ❌ 无错误提示状态
  闭环：⚠️ 缺失失败分支
```

**不通过修复：** 补充缺失的跳转目标（按钮 href/tooltip）或缺失的反馈状态（Toast/错误提示）。

## B 类：模板验收

> 仅 draw.io 两阶段架构适用。检查 page_spec 和最终 XML 是否遵循页面模板库。

### B1 — 页面类型是否正确

**定义：** page_spec 中标注的页面类型必须与需求文档中该页面的实际功能一致。

**检查方法：**

1. 读取 `原型任务清单.md` 中每个页面的类型标注（列表页/表单页/详情页/登录页）
2. 读取 `page_spec_*.md` 中 swimlane 布局表的 type 列
3. 对照检查：
   - 需求文档说「管理列表」→ page_spec type 应为 web，骨架应为列表页模板
   - 需求文档说「新增表单」→ page_spec type 应为 web/mobile，骨架应为表单页模板
   - 需求文档说「查看详情」→ 骨架应为详情页模板
   - 需求文档说「登录」→ 骨架应为登录页模板，**swimlane 内不得有 sidebar/nav 导航**

**常见错误：**
- 列表页用了表单页模板（没有表格，只有输入框）
- 详情页用了表单页模板（出现空白 input 而非键值对）
- 登录页用了后台页面模板（带侧边栏）

**不通过修复：** 重新生成该页面的 page_spec（套用正确模板）+ 重新渲染。

---

### B2 — 骨架是否正确

**定义：** 每个页面必须包含其类型模板中定义的所有固定骨架元素，不得缺失。

**检查方法：**

读取 page_spec 或最终 XML，检查以下骨架必备元素：

| 页面类型 | 必须存在的骨架元素 | 检查方式 |
|----------|------------------|----------|
| 列表页（Web） | nav + breadcrumb + ≥1 input/select（筛选）+ btn「查询」+ btn「新增」+ ≥3 table_header + ≥3 table_row + pagination + annotation_card | Grep 统计各 style_key 出现次数 |
| 表单页 | nav + ≥2 label + ≥2 input + btn「提交」+ btn「取消」+ annotation_card | 同上 |
| 详情页 | nav + breadcrumb + ≥2 label + ≥2 text_value + ≥1 tag + btn「返回」+ annotation_card | 同上 |
| 登录页 | bg + card + text_title + ≥2 input + btn_primary「登录」+ annotation_card；**不得有** sidebar/nav/breadcrumb | 同上 + 反向 Grep 确认无 sidebar |

**输出格式：**
```
[页面名]（列表页）骨架校验：
  ✅ nav | ✅ breadcrumb | ✅ 筛选区（2 input + 1 select + 查询 + 重置）
  ✅ 新增按钮 | ✅ 表格（5列×3行）| ✅ pagination | ✅ annotation_card
  骨架完整度：10/10 = 100%
```

**不通过修复：** 用 Edit 在 page_spec 中补充缺失的骨架元素行，然后重新渲染。

---

### B3 — 主区是否突出

**定义：** 每个页面必须有一个视觉上占据最大面积的「主内容区」，该区域面积必须 ≥ 页面可用面积的 50%。

**检查方法（draw.io 模式）：**

1. 计算页面可用面积 = UI 区宽 × (swimlane 高 - 导航栏高 - 底部栏高)
   - Web：1440 × (960 - 56 - 0) = 1,301,760 px²
   - 移动端：375 × (860 - 56 - 56) = 280,500 px²

2. 识别主内容区：
   - 列表页：主内容区 = 表格区（从 table_header 第一行 y 到最后一个 table_row 的 y+height）
   - 表单页：主内容区 = 字段区 card 容器
   - 详情页：主内容区 = 基础信息 card 容器
   - 登录页：主内容区 = 居中 card

3. 计算主内容区面积占比：
   - 主内容区面积 = width × height（从 page_spec 读取）
   - 占比 = 主内容区面积 / 页面可用面积

4. 判定：
   - ≥ 50%：✅ 主区突出
   - 30%–50%：⚠️ 主区偏小，建议扩大
   - < 30%：❌ 主区不突出，页面重心不明确

**常见问题：**
- 列表页表格只有 2 行数据，表格区占比过小
- 表单页字段 card 宽度不足（只用了 400px，实际可用 1392px）
- 大量标注文字挤占了 UI 区（标注区元素 x 坐标进入 UI 区）

**不通过修复：** 扩大主内容区尺寸（增加表格行数、扩大 card 宽度），或删除挤占主区的多余元素。

---

### B4 — 是否出现模板外乱布局

**定义：** 页面元素的 y 坐标顺序必须符合其类型模板的区块排列逻辑，禁止出现"筛选区跑到表格下方"、"提交按钮出现在导航栏上方"等乱序。

**检查方法：**

1. 对每个页面，按 y 坐标从小到大排列所有元素
2. 检查元素 style_key 的出现顺序是否符合模板定义：

| 页面类型 | 正确的 y 坐标递增顺序 |
|----------|---------------------|
| 列表页 | nav → breadcrumb → 筛选区(input/select/btn) → 新增btn → table_header → table_row×3 → pagination → annotation_card(标注区) |
| 表单页 | nav → breadcrumb → text_subtitle(分组) → label+input(×N) → btn_primary+btn_secondary → annotation_card |
| 详情页 | nav → breadcrumb → card → label+text_value(×N) → tag → btn → annotation_card |
| 登录页 | bg → card → text_title → input(×N) → btn_primary → text_hint |

3. 检测乱序：
   - 若 pagination 的 y < table_header 的 y → 分页跑到表头上方 ❌
   - 若 btn_primary（提交）的 y < 任何 input 的 y → 按钮在输入框上方 ❌
   - 若 annotation_card 的 x < 标注区起点 → 标注卡片进入 UI 区 ❌
   - 若 sidebar 或 nav 出现在登录页 → 骨架隔离违规 ❌

**输出格式：**
```
[页面名] 布局顺序校验：
  ✅ 元素 y 坐标递增顺序与模板一致
  ❌ pagination(y=170) 出现在 table_header(y=218) 之前 → 分页乱序
```

**不通过修复：** 用 Edit 修正元素的 y 坐标，使其符合模板顺序。

## C 类：反模式验收

> 检查原型是否"看起来像界面"而非"看起来像文档"。

### C1 — 是否说明框过多

**定义：** 标注区以外的 UI 区内，不得出现超过 2 个纯文字说明元素。原型的 UI 区应该全是可交互组件，不是文字说明。

**检查方法（draw.io 模式）：**

1. 对每个 swimlane，统计 UI 区内（x < 标注区起点）的所有 mxCell
2. 识别「纯说明元素」：style 含 `text;` 且 value 长度 > 30 个字符，且不是 label/breadcrumb/title
3. 统计数量：
   - ≤ 2 个：✅ 正常（允许页面说明标题和分组标题）
   - 3–4 个：⚠️ 说明框偏多，建议检查是否有说明文字混入 UI 区
   - ≥ 5 个：❌ 说明框过多，页面像文档而非界面

**检查方法（HTML 模式）：**

1. Grep 搜索 `<p>` 和 `<div>` 标签内纯文字（不含 input/button/a 等子元素）
2. 长度 > 50 字符的纯文字块，排除 table 内数据和 label，统计数量

**常见问题：**
- 在列表页 UI 区写了"本页面用于管理用户数据，支持增删改查操作"的大段说明
- 在表单页每个字段下方写了一整段校验规则文字（应放标注区）
- 在详情页放了需求文档原文段落

**不通过修复：** 将说明文字移至标注区（x 坐标改为标注区起点），或删除不属于原型的文字。

---

### C2 — 是否大段文字占主体

**定义：** 单个 mxCell 的 value 长度不得超过 80 个字符（标注区除外）。UI 区应该用组件表达信息，不是用大段文字。

**检查方法（draw.io 模式）：**

1. 对每个 swimlane 的 UI 区元素（x < 标注区起点），检查每个 mxCell 的 value 长度
2. 排除以下合理的长文本：annotation / annotation_card（标注区）、modal 确认文案
3. 判定：
   - value ≤ 80 字符：✅ 正常
   - 80 < value ≤ 150 字符：⚠️ 偏长，检查是否应拆分为多个组件
   - value > 150 字符：❌ 严重违规，大段文字不是 UI 组件

**检查方法（HTML 模式）：**

1. Grep 搜索所有非 `<script>` / `<style>` 区域的文本节点
2. 单个文本节点超过 150 字符（排除 table td 数据）→ 标记

**常见问题：**
- 把需求文档的功能描述整段放进了一个 mxCell
- 在按钮 value 里写了"点击此按钮后系统将自动校验所有字段并提交到后台处理"
- 把字段校验规则写在 input 的 value 里而不是标注区

**不通过修复：** 将长文本拆分为多个组件（label + value 分离），或移至标注区。

---

### C3 — 页面是否像文档/PPT

**定义：** 原型页面必须看起来像真实的应用界面，不能像 Word 文档或 PPT 幻灯片。

**检查方法（draw.io 模式）：**

对每个 swimlane 做「组件类型比例分析」：

1. 统计 UI 区内所有 mxCell 的 style_key 分布：
   - **交互组件**：input、select、textarea、btn_primary、btn_secondary、btn_sm、btn_danger、pagination、tab_active、tab_inactive、tag_*
   - **结构组件**：nav、bg、card、sidebar、bottom_bar、divider、table_header、table_row_*、modal_bg
   - **文字组件**：label、text_title、text_subtitle、text_body、text_hint、text_value、breadcrumb

2. 计算比例：
   - 交互组件占比 = 交互组件数 / UI 区总组件数
   - 文字组件占比 = 文字组件数 / UI 区总组件数

3. 判定：
   - 交互组件占比 ≥ 20% 且 文字组件占比 ≤ 60%：✅ 像界面
   - 交互组件占比 10%–20%：⚠️ 交互组件偏少，可能像静态展示页
   - 交互组件占比 < 10% 或 文字组件占比 > 70%：❌ 像文档/PPT，不像界面

**例外：** 详情页允许文字组件占比较高（≤ 70%），因为详情页本身以信息展示为主。

**检查方法（HTML 模式）：**

1. 统计 `<input>`、`<select>`、`<button>`、`<a>` 等交互元素数量
2. 统计 `<p>`、`<span>`、`<div>` 等纯展示元素数量
3. 同上比例判定

**常见问题：**
- 整个页面只有标题和大段文字说明，没有任何输入框和按钮
- 列表页没有表格，用 5 段文字描述了列表功能
- 表单页没有输入框，用文字列出了"需要填写的字段：用户名、手机号、邮箱"

**不通过修复：** 将文字描述替换为真实 UI 组件（input/table/button），按页面类型模板重构。

---

### C4 — 是否所有内容同权

**定义：** 页面必须有清晰的视觉层级——主操作按钮用 btn_primary（蓝色实心），次要操作用 btn_secondary（蓝色边框），危险操作用 btn_danger（红色）。禁止所有按钮都用同一种样式。

**检查方法（draw.io 模式）：**

1. 对每个 swimlane 的 UI 区，提取所有按钮类 mxCell（style 含 `btn`）
2. 检查样式多样性：
   - 是否存在 ≥ 2 种不同的按钮 style_key（如 btn_primary + btn_secondary）
   - 是否有主按钮（btn_primary）且仅 1–2 个（主操作不应过多）
   - 是否有危险操作使用了 btn_danger 或 btn_danger_filled（而非普通按钮）

3. 检查字号层级：
   - 页面内是否存在 ≥ 2 种不同的 fontSize（如 title=16、body=13、hint=11）
   - 是否所有文字都用同一个 fontSize → 无层级感 ❌

4. 判定：
   - 按钮 ≥ 2 种样式 且 字号 ≥ 2 种：✅ 有视觉层级
   - 按钮只有 1 种样式 或 字号只有 1 种：⚠️ 层级不够，建议区分
   - 所有按钮同色 且 所有文字同号：❌ 完全同权，无视觉引导

**检查方法（HTML 模式）：**

1. Grep 搜索 `class=` 中的按钮样式类，统计不同类名种类
2. Grep 搜索 CSS 中的 `font-size` 值，统计不同字号数量

**常见问题：**
- 列表页操作列的"查看"、"编辑"、"删除"三个按钮都是蓝色实心主按钮
- 表单页"提交"和"取消"用了完全相同的样式
- 页面所有文字都是 13px，标题和正文没有区分

**不通过修复：**
- 将次要操作改为 btn_secondary 或 btn_sm
- 将危险操作改为 btn_danger / btn_sm_danger
- 确保标题用 text_title(16px)、正文用 text_body(13px)、辅助用 text_hint(11px)
